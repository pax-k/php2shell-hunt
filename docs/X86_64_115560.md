# Action E — 115560 on x86-64 (linux/amd64)

Status: 2026-10-31. Lab-only; fixed benign command `id>/tmp/vd 2>&1`.
Target: `:18207`, container `php2shell-115560-amd64`, `php:8.4.27-apache`
(`linux/amd64`).

## 1. Environment / emulation

Host is `arm64` (Apple Silicon). Docker's amd64 emulation here is **Rosetta 2
for Linux**, not qemu-user: `/proc/<pid>/maps` contains
`/mnt/rv/[rosetta]`. All results below therefore describe amd64 userspace under
Rosetta, not a native x86-64 kernel.

```sh
docker run --platform linux/amd64 -d --name php2shell-115560-amd64 \
  -p 18207:80 \
  -v "$PWD/lab-115560/webroot:/var/www/html:ro" \
  -v "$PWD/lab-115560/php-115560.ini:/usr/local/etc/php/conf.d/zz-115560.ini:ro" \
  -v "$PWD/lab-115560/apache-single.conf:/etc/apache2/conf-enabled/zz-lab.conf:ro" \
  --cap-add SYS_PTRACE --security-opt seccomp=unconfined \
  php:8.4.27-apache \
  bash -c "mkdir -p /tmp/sessions && chmod 1777 /tmp/sessions && apache2-foreground"

docker exec php2shell-115560-amd64 uname -m          # x86_64
docker exec php2shell-115560-amd64 php -v | head -2 # PHP 8.4.27 (cli) (NTS)
```

Single prefork child (`apache-single.conf`, `MaxConnectionsPerChild 1`) for
determinism; qemu/Rosetta was fast enough (measure 2.9 s, fire 2.7 s).

## 2. Blocker: the driver's `maps.parse_maps` is arm64-shaped

```sh
python3 poc/verify_115560_vardestroy.py --target 127.0.0.1:18207 \
  --container php2shell-115560-amd64 --build 8.4.27 run
```

```
[!] maps parse failed (lib=None mains=[])
[i] no second var_destroy dtor (8.5.x shape); falling back to the single mid-parse dtor
[!] maps parse failed (lib=None mains=[])
```

Both failures are parsing, not exploit failures. Two amd64-specific mismatches
in `php2shell/maps.py`:

1. **libphp base.** It requires the r-xp mapping of libphp at file offset 0.
   On amd64 the first LOAD is `r--p` offset 0; the executable segment starts at
   offset `0x157000`:

   ```
   7ffffe007000-7ffffe15e000 r--p 00000000 ... /usr/lib/apache2/modules/libphp.so
   7ffffe15e000-7ffffe67c000 r-xp 00157000 ... /usr/lib/apache2/modules/libphp.so
   ```

   → `lib = 0x7ffffe007000` (start of the offset-0 mapping), not the r-xp start.

2. **ZendMM main chunk alignment.** It requires an anonymous rw mapping that
   *starts* 2 MiB-aligned and is exactly/at least 2 MiB. On amd64 the main chunk
   mapping starts one page **before** the boundary:

   ```
   7ffffc3ff000-7ffffc600000 rw-p 00000000 00:00 0   # 0x201000 bytes
   ```

   → the chunk base is `0x7ffffc400000` (next 2 MiB boundary), which the parser
   discards because `start % 0x200000 == 0xa000`.

No driver edit was made. New probe `lab-115560/measure_amd64.py` repeats the
same measure with x86-64-aware parsing (libphp offset-0 mapping; main =
2 MiB-aligned base containing the raw session buffer) and prints explicit
`fire` arguments for the unmodified driver.

## 6. Seed gap (no-`/proc` brute)

The measured container kernel reports `vm.mmap_rnd_bits = 18`
(`randomize_va_space = 2`). Two observations:

- **This Rosetta target is deterministic.** Six measures and five
  `docker restart` cycles all returned `main = 0x7ffffc400000` and
  `lib = 0x7ffffe007000`. Rosetta fixes the guest address layout, so the seed
  gap here is effectively **1 candidate** — no brute force needed.
- **This does not generalize to native x86-64.** On a native host with the
  x86-64 default `mmap_rnd_bits = 28`, the mmap base randomizes over
  `2^28` pages = 1 TiB; at 2 MiB slots that is **2^19 = 524288 candidates**
  (the number in `docs/PLAN_115560.md`), which is infeasible.

Two further blockers for the no-`/proc` final on x86-64:

1. The driver's `--brute` defaults (`--lo 0xFFFF78000000`,
   `--hi 0xFFFFC0000000`, 576 slots) are **arm64-shaped** and do not cover any
   `0x7fff...` x86-64 mapping. A correct window would have to be supplied
   (e.g. a 1 TiB `0x7f0000000000..0x800000000000` range).
2. `--lib-delta` and `--zif-off` are per-arch: `0x1c07000` /
   `0x46ad70` here, versus `0x20f0000` / `0x431510` on arm64.

**Conclusion:** x86-64 8.4.27 is **memory-feasible** (the chain fires once the
addresses are known; delta is arch-independent), but not self-contained on a
28-bit host. The realistic path is an in-band leak — GH-22554 (raw ZendMM
pointer, 8.4.27) — or an external LFI/SSRF/XXE seed; brute force is not viable.
8.5.12 on amd64 was not tested, and its GH-22554 leak is fixed, so it would
need a different primitive.
