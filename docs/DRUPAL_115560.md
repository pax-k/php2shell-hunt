# Drupal 11.4.11 P5 through CVE-2026-115560 → `var_destroy` → stock ZendMM terminal

**Gate G1: PASS (8.4.27 and 8.5.12).**

Lab-only. Targets are `127.0.0.1:18300/18301/18302`; the only executed
command is the fixed benign `id>/tmp/vd 2>&1`. There is no arbitrary-command
interface.

## Result

A stock Drupal 11.4.11 object graph (`YamlCacheCollectorDiscovery` →
`MenuActiveTrail` → `CacheCollector::updateCache` → `MemoryBackend::get` →
`unserialize`) is delivered through the **real** CVE-2026-115560 session
decoder (`php_serialize` upload-progress file, then `session_start()` with the
`php` handler).  `var_destroy` frees the `var_entries` chain and the re-entrant
`R:1020;` then reads the freed chunk.  With the heap-shaping described below,
the stock `$cid . ':' . __CLASS__` lock-name spray reallocates that exact
8160-byte chunk, so `data[1]` is the forged `zval *` carried in the first 8
bytes of `$cid`.  The forged reference/object reaches `zif_system` and writes
`uid=33` to `/tmp/vd` on stock ZendMM (no ASAN, no custom allocator).

## Why the spray needed heap shaping

`var_entries` is `16 + 8*1018 = 8160` bytes (two ZendMM pages).  The Drupal
lock name is `$cid . ':' . 'Drupal\Core\Cache\CacheCollector'`; with
`strlen($cid)=8102` it is 8135 bytes, and `zend_string_alloc` requests
`24 + 8135 + 1 = 8160`, the same size class.  `$cid[0:8]` holds the forged
`zval *` (`carrier + OFF_ZVAL`), which lands at chunk+24 = `data[1]`.

ZendMM large allocations use **best-fit** and take the lowest exact two-page
free run.  After `var_destroy` frees the chain chunk, lower exact-two-page
runs still exist, so the single lock-name allocation did not reach the chain
chunk.  Two attacker-controlled, persistent allocations fix the page map:

* `npad=4`: four 8135-byte strings placed in a property parsed **last**
  (`directories` after `yamlCacheCollector`).  These are 8160-byte chunks and
  occupy the lower runs that are free at `var_destroy` entry.
* `nk=65`: 65 **string-keyed** `keysToPersist`/`storage` entries.  Before the
  lock name is built, `updateCache()` fills `$data`; at 65 string keys its
  hashtable is a two-page table and stays live.  It consumes the last lower
  exact-two-page run, so the lock name takes the freed `var_entries` chunk.

Integer keys do not work: they produce a packed array whose storage is small
and never a two-page hashtable.  With `nk<=64` the table is still below two
pages (or is released), and the spray misses; `nk>=65` moves the lock name
onto the freed chain chunk.

GDB confirmation on 8.4.27 CLI (`probe_npad.py`, `probe_map3.py`):

```

               ALLOC emalloc size=8128 -> 0xfffff5f17000
               ALLOC erealloc size=8167 -> 0xfffff5f17000
               SUCCESS
```

## cleanup=On race (default profile, 18302)

The race container now uses `lab-drupal/apache-race.conf` (4/8 prefork
children, `MaxConnectionsPerChild=1`) instead of the single-child direct
profile.  The persistent first record is written by the new
`lab-drupal/endpoints/vd_seed.php`: it starts the session under the configured
`php_serialize` handler and stores

```
$_SESSION['seed_d'] = '|' . <valid a:1018 dummy>
```

so the file begins `a:1:{s:6:"seed_d";s:N:"|a:1018:{...}`.  The consumer's
`php` decoder takes the bytes before the first `|` as an ignored name, parses
the `a:1018` as record #1, then reaches the streaming upload-progress record's
`|` and parses the exploit payload as record #2.

Successful run (fresh SID/seed for measure and fire; the two requests ran on
different freshly forked children):

### Race controls

| Control | Result |
|---|---|
| `--settle 6.0` (consumer after the ~4.8 s upload window) | hold pid exists, but magic scan finds no raw input; `rc=2`; no proof |
| `--no-seed` | measure finds the payload (`delta=0x79037`), fire returns `HTTP/1.1 200 OK`; no proof |
| `--bias-zif 0x1000` | measure succeeds, fire consumer dies without writing `/tmp/vd`; no proof |

The `--no-seed` negative is the record-loop control: with cleanup=On the
progress record is the only record, so there is no record #1 and the
`R:1020` geometry does not reach the freed chunk.

### Reproduction

```sh
python3 poc/verify_115560_drupal.py \
  --target 127.0.0.1:18302 \
  --container php2shell-115560-drupal-8427-race \
  --build 8.4.27 --settle 0.7 --nchunks 8 --delay 0.6 race
```

A first measure attempt can miss before the pool is warm; the driver
re-measures with a fresh SID.  The successful evidence above used measure
attempt 1/3 and fire attempt 1/2.
