# Action C — `disable_functions`-hardened 115560 → var_destroy → `zif_system`

**LAB-ONLY.** Fixed benign command `id>/tmp/vd 2>&1`; no arbitrary-command
interface. Target: `127.0.0.1:18203`, container
`php2shell-115560-8427-nofunc`, PHP `8.4.27-apache`.

This run did **not** touch `:18200` / `php2shell-115560-8427` (full-window scan)
or `:18201` / `php2shell-115560-8512`.

## Result

`disable_functions` blocks the public simple-gadget path (`system` /
`shell_exec` are `false`, a direct `system("id")` is an
`undefined function` fatal), but the forged `zif_system` call bypasses the
disabled-function function-table stub and still runs the fixed command:

```
[f] response=<none> proof='uid=33(www-data) gid=33(www-data) groups=33(www-data)'
[EVIDENCE] 115560 session decode -> var_destroy -> uid=33
```

Control (`--bias-zif 0x1000`) produced no proof.

hardened target's Apache worker at `:18203`.

## Interpretation

- The public 115560 simple-gadget chain resolves `system`/`shell_exec` through
  the PHP function table. `disable_functions` replaces those entries with a
  disabled-function stub (and `function_exists()` returns `false`), so that
  chain cannot execute.
- The var_destroy chain forges a `zend_object` whose
  `handlers->dtor_obj` is the address of `zif_system` read from `libphp.so`.
  The call is an indirect C call, not a function-table lookup, so the
  `disable_functions` stub is never consulted. The same fixed benign command
  runs as `www-data` on the hardened worker.
- Scope is unchanged from the main lab: this is not a default-PHP RCE and the
  carrier address still comes from `/proc` measurement in this action-C run
  (the no-`/proc`/brute-force route is documented in `lab-115560/README.md`).
